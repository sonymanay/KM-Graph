Inside “Understand & Resolve” — the concepts behind each step

How a plain-language question becomes a diagnosed, grounded answer — semantic search, graph nodes and typed relationships, hybrid retrieval and grounding.

1 · Intent detection & entity extraction

An LLM reads the raw question and classifies the intent, then extracts entities — product, version, symptom, region. Meaning first; no keyword matching yet.

“Users hit an SSO redirect loop after logging in”
→ intent = sso_redirect_loop · entities = {product: Identity Connector, symptom: redirect_loop}

2 · Semantic search (embeddings + vector similarity)

The query becomes an embedding — a numeric vector capturing meaning. It is compared to every node/article embedding by cosine similarity, so “redirect loop” matches “authentication loop” even with no shared words.

3 · Graph reasoning (nodes & typed relationships)

Each match is a node in the knowledge graph. Typed edges let the system reason across multiple hops instead of returning one flat page:

Symptom —CAUSED_BY→ Cause Cause —DIAGNOSED_BY→ Diagnostic Diagnostic —RESOLVED_BY→ Fix Fix —DOCUMENTED_IN→ Article Cause —EVIDENCED_BY→ Evidence
Multi-hop traversal: SSO redirect loop → Clock skew (94%) → Check NTP → Resync time → KB1001. Confidence propagates along the path; an applicability filter drops causes that don’t match the customer’s version/entitlement.

4 · Hybrid retrieval & rerank

Three retrievers run in parallel and are fused by a reranker (reciprocal-rank fusion). Each lane catches what the others miss:

Vector
semantic match on meaning — embeddings + cosine similarity
Graph
the Symptom→Cause→Fix subgraph, filtered by version & entitlement
Keyword
exact terms / error codes (BM25) — e.g. 81002
rerank( vector ⊕ graph ⊕ keyword ) → top evidence: KB1001 v2 · case evidence · telemetry

5 · Grounded answer + provenance

The LLM composes the answer only from retrieved evidence, and every claim carries a citation. A reflection step verifies each claim against its source before it reaches the customer; then the answer is shaped to the channel.

answer = compose(evidence) · cite(KB1001 v2, case-evidence) · reflect(✓) · shape(channel)

Self-Evolving Content — an illustrative update to a Microsoft Learn article, driven by customer queries

When the case miners and community crawler detect that a recurring query isn’t fully answered by existing content, the system drafts the update and self-validates it (reflection + provenance). Routing policy then decides: low-risk, high-confidence updates publish automatically; anything that touches security, entitlements or legal wording goes to an expert first. The article version increments — so the next customer gets the better answer.
